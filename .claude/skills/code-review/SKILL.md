# Code Review

Two-axis review of the diff between `HEAD` (or the working tree) and a fixed point:

- **Standards** — does the code conform to this repo's documented conventions?
- **Spec** — does the code faithfully implement the originating issue / PRD?

Both axes run as **parallel sub-agents** so they don't pollute each other's context; this skill then aggregates their findings without merging them.

Tracker conventions live in `docs/agents/issue-tracker.md`.

## Process

### 1. Pin the fixed point

Whatever the user said is the fixed point — a SHA, `origin/main`, `HEAD~2`, a branch. If they didn't say:

- Uncommitted work in the tree → review the working diff (`git diff HEAD` plus `git status --short` for new files, which `git diff` alone misses).
- Otherwise → the commits for this slice: find them with `git log --oneline --grep "#<issue>"` and use the parent of the earliest as the fixed point.

Capture the diff command once — `git diff <fixed-point>...HEAD` (three-dot, against the merge-base) — and the commit list via `git log <fixed-point>..HEAD --oneline`.

Confirm the ref resolves (`git rev-parse`) and the diff is non-empty **before** spawning anything. A bad ref or empty diff must fail here, not inside two sub-agents.

Note anything in the diff that isn't the slice: this repo's tree routinely carries unrelated dirt (`.claude/settings.local.json`, stray worktrees, untracked `docs/`). Scope the review to the slice and say what you excluded.

### 2. Identify the spec source

In order:

1. Issue references in the commit messages (`#27`) — fetch with `gh issue view <n> --comments`.
2. A path or issue number the user passed as an argument.
3. The parent PRD named in the issue's **Parent** section — fetch it too. Its **Contracts** section is frozen and is the sharpest spec available: schema shapes, server-action signatures, routes, i18n namespaces.
4. If nothing is found, ask. If the user says there is no spec, the Spec sub-agent skips and the report says so.

`gh issue view` writes nothing to stdout in this environment when its output is piped — use `gh issue view <n> --json number,title,body,comments` and write to a file, then read it.

### 3. Assemble the standards sources

This repo has no `CODING_STANDARDS.md`. Its standards are:

- `AGENTS.md` (via `CLAUDE.md`) — **this is not the Next.js you know**: the relevant guide under `node_modules/next/dist/docs/` must be read before writing code, and deprecation notices are binding.
- `docs/agents/cross-cutting-checklist.md` — the ten recurring concerns. This is the primary standards document.
- `docs/adr/*.md` — binding decisions. An ADR outranks the code it contradicts.
- `CONTEXT.md` — glossary / ubiquitous language. New names should reuse it.
- `planning/*.md` — the phase log records why things are the way they are.

On top of the repo's own documents, the Standards axis always carries the **repo hard checks** and the **smell baseline** below. Two rules bind both:

- **The repo overrides.** A documented repo standard always wins; where it endorses something the baseline would flag, suppress the smell.
- **Skip what tooling enforces.** `tsc`, `eslint` and `next build` already run in `/verify`. Don't spend review budget on what they catch.

<repo-hard-checks>

These are the expensive things to get wrong in this codebase. Each is a **hard** finding when breached, not a judgement call:

- **Trilingual i18n** — every new public-site string has a key in all three of `src/messages/{pl,en,ua}.json`. A key in one or two catalogs is a bug. `/admin/*` is English-only by convention: pl/ua keys there are also wrong.
- **Auth gating** — user-gated actions thread `redirectTo` through *every* hop (sign-up → verify-email → profile → action), including email `callbackURL`. Admin actions go through the admin guard and live under `/admin/*`. Rendering a control is never authorization — the action re-checks.
- **Migrations** — additive only, generated by `drizzle-kit`, emitted SQL reviewed. Tables keyed by `event_slug` **text, no FK**. Legacy `teams` / `runners` / `slot_counter` are frozen. There is no events table — events are config in `src/lib/events/`.
- **Flow states** — gated / loading / empty / error, plus the event-lifecycle state (`upcoming` / `registration_open` / `full` / `registration_closed` / `completed`). A diff with only its happy path is incomplete.
- **SSG** — public event pages are statically generated across three locales. New public routes must make an explicit SSG-vs-dynamic choice; a route deletion or rename requires clearing `.next`.
- **Modal + fallback** — user-facing flows are `@modal/(.)…` intercepting routes with a hard-load full-page fallback sharing one content component.
- **Emails** — React Email templates, copy in all three locales, sends logged idempotently per `(event_registration_id, kind)`. Built in `src/features/event-mailings/`; the legacy team mailing module is frozen.
- **Reuse before machinery** — plain `useState` + `.iv-*` / `FloatField` forms (deliberately not react-hook-form), `.auth-*` / `.acl-*` tokens, `authClient` methods, the registry selectors, the signed-ticket helpers. A new abstraction alongside an existing idiom is a finding.
- **Widened unions** — when a diff adds a value to a status/enum union, every exhaustive site must handle it: `Record<Status, …>` maps, status pills, filter lists, totals, i18n label lookups, audience queries. A missing arm is a hard finding even when it type-checks.

</repo-hard-checks>

<smell-baseline>

A fixed set of Fowler code smells (_Refactoring_, ch.3) that applies even where the repo documents nothing. Each is a labelled heuristic ("possible Feature Envy"), **never** a hard violation. Read as *what it is* → *how to fix*:

- **Mysterious Name** — a function, variable, or type whose name doesn't reveal what it does or holds. → rename it; if no honest name comes, the design's murky.
- **Duplicated Code** — the same logic shape appears in more than one hunk or file in the change. → extract the shared shape, call it from both.
- **Feature Envy** — a method that reaches into another object's data more than its own. → move the method onto the data it envies.
- **Data Clumps** — the same few fields or params keep travelling together (a type wanting to be born). → bundle them into one type, pass that.
- **Primitive Obsession** — a primitive or string standing in for a domain concept that deserves its own type. → give the concept its own small type.
- **Repeated Switches** — the same `switch`/`if`-cascade on the same type recurs across the change. → replace with polymorphism, or one map both sites share.
- **Shotgun Surgery** — one logical change forces scattered edits across many files in the diff. → gather what changes together into one module.
- **Divergent Change** — one file or module is edited for several unrelated reasons. → split so each module changes for one reason.
- **Speculative Generality** — abstraction, parameters, or hooks added for needs the spec doesn't have. → delete it; inline back until a real need shows.
- **Message Chains** — long `a.b().c().d()` navigation the caller shouldn't depend on. → hide the walk behind one method on the first object.
- **Middle Man** — a class or function that mostly just delegates onward. → cut it, call the real target direct.
- **Refused Bequest** — a subclass or implementer that ignores or overrides most of what it inherits. → drop the inheritance, use composition.

</smell-baseline>

### 4. Spawn both sub-agents in parallel

Send a single message with two `Agent` tool calls, both `general-purpose`.

**Standards sub-agent** — include:

- The diff command and commit list, and which paths are in scope.
- The standards-source file paths from step 3, **plus the repo hard checks and the smell baseline pasted in full** — the sub-agent has no other access to them.
- The brief: "Report — per file/hunk where relevant — (a) every breach of a documented repo standard or of the repo hard checks: cite the standard (file + rule) and quote the hunk; and (b) any baseline smell you spot: name it and quote the hunk. Hard checks and documented standards are hard findings; baseline smells are always judgement calls, and a documented repo standard overrides the baseline. Skip anything `tsc`/`eslint`/`next build` catches. Under 400 words."

**Spec sub-agent** — include:

- The diff command and commit list.
- The fetched issue body and comments, and the parent PRD's **Contracts** section.
- The brief: "Report: (a) requirements the spec asked for that are missing or partial; (b) behaviour in the diff that wasn't asked for (scope creep); (c) requirements that look implemented but where the implementation looks wrong; (d) any silent deviation from the PRD's frozen Contracts — a contract change that wasn't surfaced is the most serious finding available. Quote the spec line for each finding. Under 400 words."

If there is no spec, skip the Spec sub-agent and note it.

### 5. Aggregate

Present the two reports under `## Standards` and `## Spec`, verbatim or lightly cleaned. Do **not** merge or rerank across axes, and do **not** report through `ReportFindings` — a single flat ranked list destroys the separation this skill exists for.

End with one line: findings per axis, and the worst issue *within each axis*. Don't pick a winner across axes.

Fixing is not part of this skill. If the user wants the findings applied, do it as a follow-up and re-run `/verify`.

## Why two axes

A change can pass one axis and fail the other:

- Code that follows every convention but implements the wrong thing → **Standards pass, Spec fail.**
- Code that does exactly what the issue asked but breaks the project's conventions → **Spec pass, Standards fail.**

Reporting them separately stops one axis from masking the other.
